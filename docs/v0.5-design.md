# v0.5 — "The village of two anchors"

Design spec for the v0.5 milestone cycle. Locks the architectural shape, feature surface, and implementation sequencing. Companion to `roadmap.md`, `architecture.md`, and `decisions.md`.

**Status:** Design locked 2026-05-09. Implementation starts M9.

---

## Goal

Stop being *"a guy in a room who remembers"* and become *"a small village where two people remember the player and each other."*

v0.5 is the cycle that takes v0.0's seed magic moment ("Raebai remembers me") and grows it into a richer surface: two anchors that maintain consolidated memory, gossip about the player, shift emotional state across conversations, and exist alongside a small ambient population that reacts to public speech.

## The bundle

Three intertwined sub-cycles, shipped as one design but sequenced into atomic milestones:

| Sub-cycle | Beat | Surface |
|-----------|------|---------|
| **a** | Two anchors gossip about the player | NPC #2 + memory consolidation + relationship registry + gossip propagation |
| **b** | Anchors' emotional state visibly shifts | D-034 (mood / trust / patience) + NPC-initiated farewell |
| **c** | A small crowd reacts to public speech | D-033 broadcast wiring + Tier 0 ambient population |

## Non-goals (deliberate exclusions)

- D-031 Tier 1 implementation — v0.5 ships Tier 0 + Tier 2 only
- Combat / inventory / equipment — Tier 1.5 work, deferred behind v0.5
- Animated NPC routines — Mirelle and ambient NPCs are stationary
- Multi-room world expansion beyond the second room — Tier 3 territory
- Mobile touch UI — D-011 stays *architecturally* respected (no keycode references) but the touch overlay isn't built
- NPC ↔ NPC valence dynamics — only player ↔ NPC valences shift in v0.5
- Player-visible state — D-020 holds; state is discoverable through voice

## Roadmap implication

`roadmap.md` Tier 1.5 currently = "core RPG primitives" (combat etc.). v0.5 reorders this — it inserts a "NPC depth" cycle BEFORE combat. Post-v0.5 state: "rich AI village, no combat." The reasoning, captured as **D-038**: NPC depth is the project's distinguishing pillar; getting two anchors + consolidation right unlocks Tier 2 directly, while combat is well-trodden territory that benefits from being designed against a richer NPC layer. `roadmap.md` will be updated when this design is committed.

## World scope

A second room is added adjacent to v0.0's existing 24×16 room, joined by a short connector (3-tile-wide passage). Approximate layout:

```
   ┌─────────────────────────┐    ┌──────────────────┐
   │                         │    │                  │
   │     Raebai's room       │====│  Mirelle's room  │
   │     (v0.0, 24x16)       │====│     (~20x16)     │
   │                         │    │                  │
   │     Raebai stationary   │    │  Mirelle + 3     │
   │     centre-east         │    │  ambient NPCs    │
   │                         │    │                  │
   └─────────────────────────┘    └──────────────────┘
```

**Camera2D bounds adjust** in `Player.tscn` so the camera follows the player across rooms without panning into void. Per-room tracking via `Area2D` covering the floor of each room — entities maintain `current_room_id` updated on `body_entered` / `body_exited` (cheap O(1) lookup, used for earshot determination in broadcast reactions).

The connector is a low-traffic corridor: stone floor, no NPCs, no proximity zones. Functions as a brief atmospheric transition (briefly empty) so the second room feels like its own place. The connector has its own room ID (`"connector"`); since no NPCs live there, broadcasts emitted from the connector reach an empty earshot list and produce no reactions. Acceptable v0.5 behaviour.

## NPC #2: Mirelle

**Working name:** Mirelle. Mid-40s. Lives in the second room — a small cottage with herbs drying outside.

**Role in village:** the unofficial news node. Knows everyone's business and shares freely.

**Personality core:** gregarious, opinionated, warm. Gossips because she *cares* about people, not to harm — sees herself as keeping the village connected. Trust grows fast but breaks loud.

**Voice contrast with Raebai:** quick where he's measured, opinionated where he's observational, concrete where he's reflective. Prefaces things with *"between you and me"* (knowing it'll spread anyway), calls people *"love"* or *"duck"*, remembers small details about *people* (not events).

**Relationship with Raebai:** old village friends. Mutually respectful but tease each other — *"Raebai's got his nose in another book again"*. They've watched the village together for years. Initial valence between them: 0.7 (deeply trusting).

**Stake in the player:** new face = fresh news. She's curious about you immediately. As trust grows, she shares richer gossip about Raebai and the village — that's the unlock for sub-cycle a's beat.

**Tier:** Tier 2 anchor (full LLM, full memory, async consolidation, behavioural state).

**Patience curve:** higher baseline rate-of-decay than Raebai. Mirelle stays engaged longer when fresh but loses interest faster when fatigued. Initial tunable: `patience_decay_rate = 0.05` (vs Raebai's 0.03). Iterate via playtest.

The full personality prompt and few-shot examples for Mirelle are drafted in M12. v0.5 budgets 1–2 prompt iteration rounds per Session 8's history (3B model character drift is an expected risk).

## Memory architecture

### The four-layer model (per `architecture.md`)

| Layer | What | Storage | Update cadence |
|-------|------|---------|----------------|
| **Persistent identity** | Name, archetype, personality prompt, voice notes | `NPCData.tres` (extended) | Hand-edited; rarely |
| **Long-term memory** | Single-paragraph LLM-generated summary of consolidated history | `user://npc_memory/<npc_id>.json` → `long_term_summary` | On consolidation |
| **Short-term memory** | Raw role/content message dicts since last consolidation | Same JSON → `short_term` | On every dialogue turn; cleared after consolidation |
| **Relationship registry** | Per-entity opinion + key facts + gossip inbox | Same JSON → `relationships` | On consolidation + on inbound gossip event |

### v2 JSON shape (per NPC)

```json
{
  "version": 2,
  "npc_id": "raebai",
  "long_term_summary": "Met Ari, a curious newcomer. He spoke of heading to Coldrose. Patient with him; he listens.",
  "short_term": [
    {"role": "user", "content": "morning"},
    {"role": "assistant", "content": "Morning, Ari. The herbs in the garden..."}
  ],
  "relationships": {
    "player": {
      "valence": 0.4,
      "key_facts": ["Newcomer to the village", "Heading to Coldrose"],
      "gossip_inbox": []
    },
    "mirelle": {
      "valence": 0.7,
      "key_facts": ["Old friend", "Village news node"],
      "gossip_inbox": [
        {"from": "mirelle", "fact": "Player asked her about the old well", "ts": "2026-05-09T14:22"}
      ]
    }
  },
  "stats": {
    "mood": 0.1
  }
}
```

`valence` is the "trust toward this entity" scalar — keeping the architecture-md term for extensibility (NPCs will eventually have valences for other NPCs, factions, etc.). `mood` is NPC-wide. **Patience is runtime-only** — resets to 1.0 on each engagement, never persisted.

### Consolidation triggers (hybrid)

| Event | Behaviour |
|-------|-----------|
| **On disengage**, if `short_term.size() ≥ 15` | Async consolidation (HTTPRequest fires; player keeps moving). Consolidation does NOT gate next engagement. State swap rules: (a) if consolidation has completed by engage time, atomic-swap long_term + relationships into the running NPC instance at the engage moment, then start fresh short_term; (b) if consolidation is still in-flight at engage time, proceed with current (stale long_term + non-empty short_term) state and defer the swap — when consolidation eventually completes, write only to the JSON file, do NOT mutate the running instance mid-conversation; the file's fresh state will be picked up by the next disengage→engage cycle. Stale long_term mid-conversation is acceptable. |
| **On disengage**, if `short_term.size() < 15` | No consolidation |
| **On quit**, any NPC with `short_term.size() > 0` | Blocking consolidation before save. **Parallel HTTPRequests** if multiple NPCs need consolidation (Ollama supports concurrent requests against the same model). Brief "saving..." overlay. |

The 15-turn threshold (down from initial 20) prevents accumulation in long sessions while still avoiding waste on short bursts.

### The consolidation LLM call

POST `/api/chat` with `format: "json"` (Ollama's grammar-constrained JSON mode — forces valid JSON output, ~95%+ reliability on Llama 3.2 3B) and `keep_alive: "30m"` (keeps model warm through realistic play sessions).

**Prompt structure (compact):**

```
You are summarizing {npc_name}'s recent conversation for long-term memory.

Personality: {personality_prompt}
Current long-term: {long_term_summary}
Relationships (compact): {relationships_compact}

Recent conversation:
{short_term_messages}

Return JSON only, exact shape:
{"updated_long_term_summary":"<= 80 words","relationship_updates":{"player":{"valence_delta":0.0,"new_facts":["..."],"consumed_inbox_indices":[]}},"mood_delta":0.0,"strong_facts_to_share":[{"about":"player","fact":"...","share_with":["mirelle"]}]}
```

Shape-by-example, not schema-by-prose — LLMs follow this better and it's terser.

**Output bounds:** `updated_long_term_summary` capped at 80 words; `new_facts` capped at 3 short phrases per entity. The LLM sees these caps in the JSON example.

**`strong_facts_to_share`** is the gossip-event firing point. Facts the NPC considers strong enough to mention to specific others. After consolidation completes, those facts get written into the target NPC's `relationships[about].gossip_inbox`. Friendship gate: target's `relationships[A.npc_id].valence > 0.3`.

### Failure handling

| Failure | Recovery |
|---------|----------|
| HTTPRequest fails (Ollama down) | Log; abort consolidation; short_term preserved; retry on next trigger |
| JSON parse fails | Log; conservative fallback — concatenate short_term verbatim into `long_term_summary` (truncated to 1000 chars), no relationship/mood updates |
| Crash mid-consolidation | save file unchanged (consolidation hasn't written yet); on next launch, short_term still present; retry on next disengage |

### Migration v0.0 → v0.5

On first v0.5 launch, for each `version: 1` save:
1. Wrap as v2: `messages` → `short_term`, empty `long_term_summary`, empty `relationships`, default `stats`
2. Save as v2 immediately
3. Next disengage triggers consolidation against the migrated short_term, producing real long-term + relationships

No upfront cost; conversion happens on the next natural consolidation. Tested by launching v0.5 with Raebai's existing v1 save and verifying continuity.

### System prompt assembly at dialogue time

Stable prefix order for KV-cache reuse across calls in a session:

```
{personality_prompt}

What you remember from before:
{long_term_summary}

{compact_relationship_block_for_player}
{compact_relationship_block_for_each_relevant_other_entity}

Right now you are feeling: {mood_word}.
Your patience for this conversation: {patience_word}.

[chat history follows: short_term messages]
```

**Compact relationship encoding:** one line per entity:
```
Mirelle [warm, deeply trusting] — old friend, village news node. Recent: Raebai said X.
```

**Inactive-relationship omission:** always include `player`. Include other entities only if mentioned in the last 5 turns OR have unconsumed gossip_inbox items.

Numbers map to words via fixed bands:

| Scalar value | Word |
|--------------|------|
| `valence > 0.6` | `deeply trusting` |
| `valence > 0.2` | `warm` |
| `valence > -0.2` | `neutral` |
| `valence > -0.6` | `cold` |
| `valence ≤ -0.6` | `hostile` |
| `mood > 0.5` | `bright and open` |
| `mood > 0.2` | `settled` |
| `mood > -0.2` | `even` |
| `mood > -0.5` | `gloomy` |
| `mood ≤ -0.5` | `dark` |
| `patience > 0.8` | `fresh and curious` |
| `patience > 0.5` | `engaged` |
| `patience > 0.2` | `fading` |
| `patience ≤ 0.2` | `worn out, ready to leave` |

The LLM never sees a raw float — D-020 holds (no numeric optimisation surface), and 3B models reason far better on natural language than scalars.

## Behavioural state — D-034 wiring

### The three scalars

| Scalar | Range | Persisted | Update mechanism | Decay |
|--------|-------|-----------|------------------|-------|
| **Mood** | -1.0 to +1.0 | Yes (`stats.mood`) | LLM-inferred at consolidation (`mood_delta`) | -0.05 toward 0 per consolidation cycle (no day/night clock until Tier 3) |
| **Trust** (per entity) | -1.0 to +1.0 | Yes (`relationships[entity].valence`) | LLM-inferred at consolidation (`valence_delta`) | None |
| **Patience** (current convo) | 0.0 to 1.0 | **No** (runtime only) | **Rule-based, per turn** | Resets to 1.0 on engage |

### Patience: rule-based per-turn

Each player turn applies a delta. Cumulative across the conversation. Triggers NPC-initiated farewell when below 0.2.

| Trigger (regex/heuristic) | Δ patience | Why |
|---------------------------|------------|-----|
| Default per-turn baseline | -`patience_decay_rate` (per-NPC) | Conversations naturally wind down |
| Insult/profanity match | -0.25 | Sharp impatience response |
| Repeated question (Levenshtein < 5 from any prior player turn) | -0.10 | NPCs notice when they're being looped |
| Direct farewell-keyword (existing D-037 regex) | (instant close, no patience needed) | Already handled |
| Aligned-with-interest match (lightweight keyword set) | +0.05 | Engagement renews patience |
| Compliment match | +0.10 | Warmth extends patience |

`Δ` clamped at the bounds.

**Regex compilation:** all patience-delta regexes compile once at `_ready()`, never per-turn. Patience computation is signal-driven (fires on `text_submitted`), never polled.

### NPC-initiated farewell

When NPC's patience crosses 0.2 (downward) at the start of their next turn:

1. Next dialogue request to Ollama receives a one-shot system addendum (cleared after use, like Session 9's callback-greeting pattern):
   > *"Your patience for this conversation is worn out. End it naturally with a brief parting line that fits your personality. Don't be rude unless your trust is also low."*
2. NPC's reply lands as usual on their bubble.
3. Engine runs the existing D-037 farewell regex over the NPC's reply.
4. If matched, fire same instant-close flow as D-037's player-side: input bar closes, player movement freed, save fires, consolidation may trigger.
5. NPC also gets a `low_patience_dismissals` counter incremented in `relationships.player` (so repeated dismissals can shape trust over time at consolidation).

### Behavioural propagation across surfaces

| Surface | How state shows up |
|---------|-------------------|
| Whisper dialogue | NL prompt injection + content shifts |
| Broadcast reaction (anchor) | LLM call with state in shallow prompt — anchor's reaction reflects current mood/trust |
| Callback greeting (existing) | Already references long-term summary; now also injects current mood/trust words |
| NPC-initiated farewell | Triggered by patience < 0.2; phrased per current trust toward player |
| Gossip emission | At consolidation, `strong_facts_to_share` correlates with high `|valence_delta|` |

## Tier system + ambient population (D-031 in v0.5)

Only **Tier 0** and **Tier 2** are implemented. Tier 1 deferred to a later cycle when a Tier 1 character (shopkeeper, guard) is genuinely needed.

| Tier | Members in v0.5 | E behaviour | Memory | Broadcast reaction |
|------|-----------------|-------------|--------|-------------------|
| **2** anchor | Raebai, Mirelle | Opens whisper dialogue UI | Full 4-layer model + consolidation | LLM call with state-aware shallow prompt |
| **1** side char | *(none in v0.5)* | n/a | n/a | n/a |
| **0** ambient | 3 NPCs in second room | Does nothing | None | Canned line, keyword-biased |

### NPCData extensions

```gdscript
class_name NPCData extends Resource

# Existing (v0.0)
@export var npc_id: String
@export var npc_name: String
@export var personality_prompt: String
@export var stats: EntityStats

# New in v0.5
@export var tier: int = 2  # default 2 keeps existing behaviour
@export var patience_decay_rate: float = 0.05

# Tier 0 only
@export var canned_greetings: Array[String] = []
@export var canned_reactions_neutral: Array[String] = []
@export var canned_reactions_hostile: Array[String] = []
@export var canned_reactions_friendly: Array[String] = []
@export var canned_reactions_curious: Array[String] = []
```

**Backwards compatibility:** the existing `first_npc.tres` (Raebai's) doesn't have the new fields; Godot's resource loader falls back to defaults — no manual migration needed.

### Tier 0 ambient — proximity + reaction behaviour

**Proximity:** entering the ambient NPC's small proximity area (~24 px radius, smaller than anchor's 32 px) triggers a random pick from `canned_greetings`. Renders in their bubble for ~3 s, then auto-fades. **No "[E] Talk" hint** — pressing E does nothing.

**Broadcast reaction logic:**

```
on broadcast(player_text):
  bucket = classify_once(player_text)   # ONE regex run, result reused
     hostile  if matches insult/profanity/threat
     friendly if matches greeting/compliment
     curious  if ends with "?" or matches who/what/why
     neutral  otherwise
  for each Tier 0 NPC in earshot:
    line = random pick from canned_reactions_<bucket> or neutral fallback
    render line in NPC's bubble after random 0–500ms delay
    bubble auto-fades after ~3s
```

**Earshot:** `current_room_id` lookup, O(1). Player and NPC must share room ID.

### Three ambient NPC archetypes for v0.5

All three use the same placeholder `ColorRect` sprite system from v0.0 — distinguished by colour only at 16×16:

| Archetype | Colour | Voice |
|-----------|--------|-------|
| **The village child** | Yellow | Direct, naive, easily impressed |
| **The grizzled local** | Grey-green | Laconic, sceptical, dry |
| **The passing trader** | Brown | Transactional, distracted |

Specific canned line sets get drafted at M14 implementation; the design locks the slot count and archetypes.

## Gossip propagation (architecture.md rule-based)

### Mechanism

1. NPC A's consolidation runs. LLM emits `strong_facts_to_share` array.
2. After A's save lands, engine iterates the array. For each `{about, fact, share_with: [npc_ids]}`:
   - For each target NPC ID in `share_with`:
     - If target's save exists AND target's `relationships[A.npc_id].valence > 0.3` AND both in same settlement (always true in v0.5):
       - Append `{from: A.npc_id, fact, ts: now}` to target's `relationships[about].gossip_inbox`
       - Cap inbox at 10 items per entity (drop oldest); when consolidation reads inbox and finds > 5 items, the older `N - 5` items are condensed into a single summary line at prompt-assembly time (before the LLM call), and only the freshest 5 are passed individually
     - Save target's JSON
3. Next time player engages target NPC, system prompt includes inbox items as `Recent rumours:` block with attribution.
4. At target's next consolidation, inbox is processed; `consumed_inbox_indices` marks which items were merged into target's perspective. Engine drops them.

### Key design property

The LLM never mediates gossip *transmission* (rule-based, deterministic) but always mediates gossip *expression* (Mirelle's words about what Raebai told her are LLM-generated from the prompt that includes the gossip).

### v0.5 simplification

Since neither anchor walks routines, "routine encounters" is short-circuited — gossip propagates immediately at consolidation time. When NPC routines land in a later tier (Tier 3+), this gates on actual proximity events.

### The videoable beat playthrough

1. Player tells Raebai about heading to Coldrose. Disengages.
2. Raebai's consolidation runs async. Strong fact identified.
3. Engine writes that into Mirelle's `relationships.player.gossip_inbox`.
4. Player walks to second room, engages Mirelle.
5. Mirelle's system prompt includes the rumour block.
6. Mirelle says: *"Heard you're off to Coldrose, love. Raebai's already told me half of it."*

## Broadcast reactions (D-033 deferred half)

When player submits a broadcast (Enter):

```
on broadcast_submit(text):
  render player speech bubble (existing)
  close input bar (existing)

  bucket = classify_once(text)
  earshot_npcs = NPCs where current_room_id == player.current_room_id

  for npc in earshot_npcs:
    if npc.tier == 0:
      schedule canned reaction (per Tier 0 logic above)
    elif npc.tier == 2 and npc != _engaged_npc:
      fire async LLM reaction call with shallow prompt
        (personality + state words + valence-toward-player only;
         no long_term, no short_term, no gossip_inbox)
        addendum: "You overhear someone shouting nearby:
                  '{text}'. Give a brief in-character reaction —
                  one short sentence. Do NOT initiate a 
                  conversation, just react."
        on response: render in npc's bubble for ~4s
```

**Cost ceiling for v0.5:** max 1 LLM call per broadcast (only Mirelle in second room; Raebai is cross-room when player broadcasts in second room).

**Patience side-effect:** broadcasts containing hostile keywords also drop the patience of any in-earshot Tier 2 anchor (but only by half the conversation rate — they're not engaged, just overhearing). So shouting insults near Mirelle makes her actually pissed when you next engage her. The same `Patience` utility from M11 is called with the half-rate flag.

**Bubble collisions:** existing SpeechBubble.gd shrink-to-fit + per-character anchoring handles up to 5 simultaneous bubbles in second room (3 ambient + Mirelle + maybe Raebai if cross-room broadcasts ever land). Visually busy but correct. Bubble pooling deferred (YAGNI for v0.5 scale).

## Token + engine efficiency principles

These apply across all surfaces above.

### LLM-side

| # | Principle | Where it bites |
|---|-----------|----------------|
| 1 | KV-cache friendly prefix order: personality + long_term FIRST, never reordered between calls | All whisper dialogue calls |
| 2 | Compact one-line relationship encoding | System prompt assembly |
| 3 | Lower consolidation trigger from 20 → 15 turns | Consolidation trigger |
| 4 | Bounded consolidation outputs: long_term ≤ 80 words; `new_facts` ≤ 3 phrases | Consolidation prompt |
| 5 | Shallow prompt for broadcast reactions: personality + state + valence ONLY | Broadcast LLM call |
| 6 | Gossip inbox compression at consolidation when > 5 items | Consolidation + future prompts |
| 7 | Skip relationship blocks for entities not mentioned recently | System prompt assembly |
| 8 | Set Ollama `keep_alive: "30m"` on every API call | All LLM calls |
| 9 | Parallel HTTPRequests on quit consolidation | Quit save flow |
| 10 | Don't gate engagement on in-flight consolidation; deferred-swap (see Memory section state-swap rules) | Engage path |
| 11 | Schema-by-example (terse JSON sample) instead of schema-by-prose | Consolidation prompt |

### Engine-side

| # | Principle |
|---|-----------|
| 12 | Compile regex once at `_ready()`, never per-turn |
| 13 | Patience updates signal-driven, never polled |
| 14 | Classify broadcast text ONCE per broadcast; reuse bucket for all ambient reactions |
| 15 | Earshot via `current_room_id` lookup, not per-broadcast distance check |
| 16 | Token estimator utility logs per-call estimate + cache-hit flag |
| 17 | Shared Patience utility used by both M11 (whisper) and M14 (overhear) |

### Cost ceilings (after optimisations)

| Call type | Estimate |
|-----------|----------|
| Whisper follow-up turn (KV-cache hit) | ~150 tokens new |
| Whisper first-turn after engage | ~480 tokens |
| Consolidation | ~870 in / ~120 out |
| Broadcast Tier 2 reaction | ~250 tokens |
| Tier 0 canned reaction | 0 tokens |
| Quit pause (2 NPCs, parallel) | ~5–10s |
| Cold-start after pause (within 30 min) | ~0s (keep_alive) |
